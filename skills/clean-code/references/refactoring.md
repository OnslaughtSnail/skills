# 渐进重构与验证

适用于已有实现的结构调整。目标是形成可解释、可验证、已收敛的改动。
以下执行约束结合原书案例与 Agent 工作特点编写。

## 一、建立行为边界

从需求、调用者、测试、接口文档和历史兼容约定交叉确认当前契约。
源码说明实际行为，测试说明已验证部分；二者都不能单独决定全部预期。

| 维度 | 在相关时确认 |
| --- | --- |
| 输入与输出 | 有效范围、缺省、空值、顺序、精度、编码 |
| 失败 | 可判别错误、部分结果、是否允许重试 |
| 副作用 | 写入、通知、网络调用、资源取得及执行次序 |
| 状态 | 所有者、不变量、事务或同步边界 |
| 兼容 | 公开符号、序列化、配置、持久化、外部调用者 |
| 非功能约束 | 有依据的延迟、吞吐、内存、平台要求 |

只记录本次会触及的契约。不要为小改动补写整份架构文档。
若发现已有 bug，先确认需求依据，再单独标明允许改变的行为；重构不能掩盖功能决策。

## 二、选择验证

- 新行为或已确认缺陷：优先用一项清楚的行为用例确定预期；条件允许时先确认它在旧代码上失败。
- 高风险遗留路径且缺少保护：添加特征测试、边界测试或可重复的最小复现，保护需要保留的行为。
- 纯局部改名、移动或格式整理：复用现有类型检查、构建和相关测试，不机械新增测试。
- 外部依赖行为未知：做最小学习实验；只把有长期价值的契约留为测试。
- 端到端行为依赖多组件时：补充对应集成验证；不能由私有函数测试推断外部系统已正确。

特征测试记录的是现状。若现状违背已确认需求，不能把它永远固化为正确行为。
记录已有失败，区分基线问题与本次回归；不能把失败环境说成已通过。

## 三、做一个最小有效步骤

选择最接近问题的动作：改名、澄清条件、抽取有意义的概念、内联浅层转发、搬移归属错误的逻辑、集中同一不变量。
修改前能说明预期收益；修改后检查收益是否实际成立。

- 数据从参数流入通常比隐含读共享字段更易追踪；不要为了短签名扩大可变状态。
- 调用顺序需要保护时，让拥有完整操作的函数维护它；不要拆成要求调用者记住顺序的碎片。
- 缩短函数时，保留算法和事务中必须一起理解的部分。
- 重复知识应该统一，但职责已分化的代码不必强行共享。
- 不在一次未验证改动上叠加另一套架构。失败先定位并恢复可工作的状态。

## 四、迁移必须有终点

确需过渡实现时，先明确旧入口、新入口以及谁拥有状态，再迁移一条路径。
每迁移一部分就验证对应行为，全部切换后检查：

- 旧分支是否仍被调用，兼容层是否仍承担公开契约；
- 临时双写、两份可变映射、重复默认值是否已收敛；
- 转发函数、测试替身和注释是否仍有实际作用；
- 失败、回滚和关闭路径是否也使用同一份最终状态。

不得在不清楚原始不变量时靠更多 fallback、缓存或恢复标记维持表面可用。

## 五、验证容易被“清理”改变的地方

| 变化 | 需要保留或明确授权修改的行为 |
| --- | --- |
| 简化条件 | 0、空串、False、None 等是否被错误合并 |
| 返回空集合 | JSON 的 null 与 []、缺失与空内容的区别 |
| 统一异常 | 调用方能否继续识别拒绝、超时与不存在 |
| 重命名或删除 | 配置、反射、插件、序列化和仓库外调用 |
| 拆分方法 | 调用顺序、事务、锁及资源释放是否被打断 |
| 改写日期／索引算法 | 闰日、月末、精度、编号原点和开闭区间 |
| 引入缓存 | 谁更新、何时失效、失败后是否仍与权威状态一致 |

单元测试全绿仍可能漏掉公共契约。风险位于边界时，应在边界上验证。
使用数据差分或性质验证时，确保比较目标正确；两份实现输出相同并不证明原有 bug 已修复。

## 六、结束条件

重新从入口阅读新代码，核对：

1. 指定目标完成，必要行为仍成立，授权改变的行为有证据。
2. 实际减少了必须同时理解的细节、重复知识或修改扩散。
3. 没有把复杂度搬到共享状态、配置、测试替身或调用协议。
4. 过渡物已清理，兼容层用途明确。
5. 必要验证已执行；受环境限制的部分有准确说明。

如果抽取后更难理解，内联或撤回该步骤。无需为了证明做过工作而保留改造。
仅为个人偏好继续整理时停止。
