# 并发与生命周期

在拆分包含共享状态、异步任务、锁、队列、取消或关闭的代码前读取本文件。
可读性改善必须保留完整不变量；短函数和单方法线程安全都不足以证明组合操作正确。

## 先明确四件事

1. **所有者**：谁创建、读取、更新和销毁状态或资源？
2. **不变量**：例如同一任务只有一个认领者、成功写入后才确认、关闭后不再接受工作。
3. **原子范围**：哪些读取、判断、修改必须不可分割？锁、事务、原子原语或队列在哪里提供保证？
4. **结束条件**：谁发出取消，阻塞如何解除，谁等待退出，资源何时释放？

没有清楚答案时，先追踪实现和调用，不通过加锁、加 goroutine 或加重试猜测修复。

## 审查共享操作

- 逐项检查读改写；一行表达式不代表原子操作。
- 每个 getter、setter 都加锁，不意味着“查是否存在 → 写入”整体安全。
- 尽量由状态所有者提供完整原子操作，使调用方不必复制锁规则。
- 缩小锁范围时，不得把不变量拆开。将耗时 I/O 移出锁前，确认是否需要版本校验、预留或提交步骤。
- 优先考虑不可变输入、请求局部数据和明确所有权；不要仅为减少参数引入共享字段。
- 已使用线程安全容器时，仍要核对组合操作与迭代保证。

## 审查生命周期

| 阶段 | 必须回答的相关问题 |
| --- | --- |
| 启动 | 初始化完成前是否被发布？启动失败由谁回收？ |
| 接收 | 并发量、队列和连接等资源是否有合理边界？满载如何反馈？ |
| 执行 | 失败、取消或超时能否解除所有等待？重试会否重复副作用？ |
| 停止 | 停止接收、通知退出、等待和释放的顺序是否一致？ |
| 恢复 | 若任务支持恢复，何种状态证明上一次操作已完成或尚未完成？ |

只落实任务实际需要的机制，不因检查表而新增恢复协议或后台管理框架。
通知了停止，不等于工作已经结束；取消返回也不必然证明远端操作未发生。

## 死锁、饥饿与性能

- 把互斥锁、连接池、队列容量和任务等待一起看作资源依赖；检查循环等待和获取顺序。
- 排队或优先级调整可能导致饥饿；重复退让和重试可能产生活锁。
- 并发只在实际负载与瓶颈支持时增加。记录测量条件，不照搬旧语言版本中的性能断言。
- 单一大锁可能正确但吞吐差；复杂无锁结构也可能无收益。先满足正确性，再按测量决定优化。

## 有针对性的验证

- 先验证不依赖并发的业务逻辑，再验证调度、同步和生命周期。
- 为具体交错设计屏障、可控制依赖或故障注入，覆盖竞争、取消、关闭和部分失败。
- 竞争检测器能发现它覆盖的竞争；没有报告不代表业务操作具有原子性。
- 压测和多平台验证按部署风险选择；不要为每次小改动强制全平台完整测试。
- 不用长 sleep 或无限重试隐藏不确定性。偶发失败仍是待解释证据。
- 说明验证的场景和范围，不宣称测试穷尽了所有执行顺序。
