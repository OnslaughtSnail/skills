# 代码质量判断

这是任务中的检查入口，不是必须逐项整改的配额。先找实际成本，再选最小动作。
下列判断采用通用工程语义；书籍与补充来源的对应关系见 sources.md。

## 命名与信息

- 名称应让调用者知道对象的角色、操作意图、单位和有效范围。同一概念保持一致用词；不同概念不要为统一名称而混淆。
- 看到 data、info、manager、flag 等模糊名称时，先读使用点；能指出被隐藏的语义再改名。短作用域惯用名可以保留。
- 区分原始值与转换值、索引与长度、秒与毫秒、排他与包含端点。语义容易混淆时优先用明确名称、类型或边界转换。
- 数值隐藏业务规则或单位时，用领域名称、常量或已有配置表达；不把所有自明的 0、1 都包装成符号。
- 公开名称属于兼容面。局部改名也要检查注册字符串、序列化标签、配置及生成入口，不能只替换文本。

## 函数与控制流

- 用一项完整的职责描述函数；解析、计算、持久化和展示混在一起，且分别变化时，考虑划界。
- 主流程应显示关键决策；细节可以抽取，但函数名和参数必须足以说明契约。原子更新、算法推导等紧密相关步骤可以放在一起。
- 多层嵌套时检查能否用守卫返回简化，同时核对清理与副作用顺序。不得为了单出口增加状态或嵌套。
- 多参数时检查是否容易传反、存在自然领域聚合或混入无关职责。不要把无关参数塞入 Options，只为降低数量。
- 布尔参数若切换两套独立流程，可考虑分别命名的操作；真实布尔属性、公开兼容参数及清晰的关键字参数可以保留。
- 保留清楚的有限分支。只有重复分派造成实际修改扩散时，才比较表驱动、多态或局部函数等方案。

## 状态、副作用与顺序

- 名为查询或判断的方法若写入、发请求、清空缓存或取得锁，应让调用契约显露这种效果。
- 检查 prepare → run → reset 等调用协议。能用输入输出、一次完整操作或构造后有效的对象表达时，减少隐含顺序。
- 不把带结果的写入拆成先查后改；claim、取队列元素、CAS 等应维持完整原子边界。
- 每项可变事实明确所有者。派生值可以缓存，但必须有更新／失效规则；不要另加可独立修改的副本来修补不清晰边界。

## 重复与抽象

- 询问两段代码是否由同一条规则支配、是否必须一起变化。若只是外形相似而政策独立，不强制消重。
- 相同不变量、错误映射或单位转换在多处维护且可能分歧时，优先集中。
- 共用函数不断增加模式参数、特例或调用方类型判断时，检查是否混合了不同概念。必要时内联，再提取真正稳定的共同部分。
- 转发层可以承担协议隔离、权限、生命周期或替换边界；只有“多绕一层”且无具体职责时才考虑移除。

## 注释与格式

- 保留业务理由、算法依据、边界约束、并发不变量、兼容原因、使用契约、版权／许可说明及有用的风险提醒。
- 删除前先核实：注释是否已过时、误导，或仅重复显然的语句。不能因为代码“应当自解释”就删除协议和数学说明。
- 普通注释不能弥补错误名称或隐蔽逻辑；可以在当前范围内改善表达。公共 API 文档与逐行注释用途不同。
- 用项目格式工具；把紧密相关定义放在容易共同阅读的位置。不要夹带全仓格式化或个人风格迁移。

## 对象、数据与变化边界

- 若目标是保护不变量，让持有数据的模块提供必要操作；若只是传输数据，允许简单结构体／记录，不为其生成无意义方法。
- 穿透对象多层内部结构可能造成表示耦合；把链式表达式拆成几个局部变量不能解决这个问题。
- 根据真实变化原因拆分模块，观察状态和方法是否围绕同一职责。不能仅凭类大或文件长就确定拆分。
- 外部依赖的类型、错误和生命周期在多处扩散时，评估窄边界；单次直接调用可能已经足够简单。
- 构造与配置在明确入口完成，运行逻辑接收所需依赖。简单构造参数足够时不增加容器、注册表或全局工厂。
- 清楚指出哪一种变化被边界挡住。没有可解释收益的接口、继承、DTO 拷贝及适配层，不因设计模式名称而成立。

## 错误与缺失

- 列出调用者应采取的动作：重试、拒绝、忽略、回滚或上报。错误分类必须保留这些差别。
- 在边界添加必要上下文并保留原因；不要在每层重复记录同一错误，或用字符串改写丢失可判别的错误身份。
- 区分合法缺失、空集合、无效输入和执行失败。只在等价语义内使用空对象或默认值。
- 检查资源关闭、事务结束和部分成功。避免清理失败覆盖主错误，也不要只返回错误而留下错误的状态。
- 必须有具体恢复契约才能加入重试；检查幂等、取消、总时限和重复副作用。

## 测试与维护

- 测试应清楚展示输入、动作和预期行为；同一概念可以用多个断言。不要为断言数量引入额外继承或测试框架。
- 让用例相互独立、结果可重复、能自动判定，并及时覆盖新行为；保持反馈足够快，按风险选择必要测试范围。
- 检查测试是否会在目标行为破坏时失败。只断言“无异常”、只验证 mock 调用次数，可能遗漏真正结果。
- 用可控制的时间、随机性和依赖减少不稳定性；仅在它们影响当前验证时引入测试接缝。
- 修改公开契约、持久化、并发或边界转换时，选择能覆盖该契约的验证层级。
- 覆盖缺口和失败模式帮助发现风险；不得把覆盖率增幅或新增用例数量当作改善证明。
- 死代码清理先确认入口与兼容性。历史实现可由版本控制保存，但仍被调用的兼容层不是死代码。

## 把观察写成可审查的问题

使用“位置 → 事实／触发条件 → 影响 → 最小方向”组织发现。
例如指出“当两个调用并发时，读取和写入之间可交错，导致同一资源被两次认领”，比“违反单一职责”更可复核。
维护性问题同样要给出具体证据，如新增一种错误需同步修改多个相同映射。
无法确认影响时记录待核实条件；不要把推测包装成缺陷。
